# API architectures expose novel XSS attack surfaces

API-specific XSS vulnerabilities represent a distinct and expanding attack class in 2024-2026, driven by the proliferation of protocol formats (REST, GraphQL, gRPC-Web, tRPC, WebSocket, SSE), multi-layered processing pipelines, and the fundamental tension between API infrastructure that processes data and frontends that render it. The most significant finding across this research is that **WAFs systematically fail to protect API traffic**: the WAFFLED methodology confirmed **1,207 bypass requests across five major WAF vendors** (AWS WAF, Azure WAF, Google Cloud Armor, Cloudflare, ModSecurity) by mutating only the HTTP structure while keeping the attack payload constant ([WAFFLED Paper](https://arxiv.org/html/2503.10846v1)). Parameter pollution bypassed **14 of 17 major WAF configurations** tested in August 2025 ([CyberSecurityNews](https://cybersecuritynews.com/wafs-protection-bypassed/)). These failures are not edge cases -- they reflect a systemic architectural gap where WAFs and backend frameworks parse the same HTTP request differently. Concurrently, API documentation tools (Swagger UI, GraphiQL), authentication flows (OAuth, SAML), file upload endpoints, webhook receivers, and server-sent event streams each introduce protocol-specific XSS vectors that traditional web application testing methodologies miss. The defense hierarchy that emerges is clear: output encoding at the rendering layer is the primary control, Content-Type headers with `nosniff` are essential but insufficient, and WAFs are defense-in-depth only, never primary protection.

## REST and GraphQL responses carry XSS through Content-Type confusion and IDE rendering

REST API endpoints remain vulnerable to XSS primarily through **incorrect Content-Type headers** -- serving responses as `text/html` instead of `application/json` -- rather than through direct JSON body sniffing, which modern browsers have largely mitigated through Opaque Response Blocking. CVE-2025-11925 demonstrated this pattern in BLU-IC2/IC4 devices, where API replies used `text/html` Content-Type instead of `application/json`, enabling HTML/JavaScript injection into responses ([Kodem Security](https://www.kodemsecurity.com/cve-database/cve-2025-11925)). CVE-2025-32960 in the Jmix REST API add-on allowed uploads to the `/files` endpoint that were served back with `text/html` for `.html` files, creating stored XSS ([GitLab Advisory](https://advisories.gitlab.com/pkg/maven/com.haulmont.addon.restapi/restapi-rest-api/CVE-2025-32960/)). The `X-Content-Type-Options: nosniff` header prevents browsers from sniffing `application/json` as HTML, but does nothing against client-side DOM injection where JSON values are inserted into HTML via `innerHTML` -- a growing vector that Content-Type headers alone cannot address ([Elixir Forum](https://elixirforum.com/t/can-json-have-a-xss-bug/13201)).

GraphQL introduces XSS risks through its tooling ecosystem rather than the protocol itself. The most persistent vector is **GraphiQL**, where CVE-2021-41248 (XSS through malicious schema introspection responses) still affects enterprise deployments in 2026 -- IBM's April 2026 bulletin confirmed it affects watsonx.data 2.3 ([IBM Support](https://www.ibm.com/support/pages/node/7268847)). CVE-2026-42794 added a new reflected XSS in GraphiQL's escaping function, which handles single quotes and newlines but fails to escape backslashes, allowing an attacker to break out of a string context via the `query` GET parameter ([Stack.watch](https://stack.watch/vuln/CVE-2026-42794/)). Spring for GraphQL disclosed CVE-2026-59286, where **missing Subresource Integrity (SRI)** on CDN-loaded scripts in GraphiQL integration created an XSS risk through CDN compromise, affecting versions 1.0.0 through 2.0.4 ([Stack.watch](https://stack.watch/vuln/CVE-2026-59286/)). The @urql/next library (CVE-2024-24556) represents a newer class where the vulnerability lies in the client-side framework's streaming/hydration mechanism: all versions before 1.1.1 failed to escape HTML-like characters in JSON payloads injected into React Server Component hydration bodies ([Tenable](https://tenable.com/cve/CVE-2024-24556)).

JSONP callback injection persists despite CORS being widely available as a replacement, with the same root cause recurring: servers echoing the callback parameter into `application/javascript` responses without validating it as a legal JavaScript identifier. CVE-2026-42548 in Flight PHP scored **CVSS 8.6** because the `?jsonp=` value was not validated ([GitLab Advisory](https://advisories.gitlab.com/composer/flightphp/core/CVE-2026-42548/)). CVE-2026-49294 in Valhalla routing engine affected versions 3.6.3 and earlier, unfixed at publication, where injected script ran in the serving origin enabling session token theft ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-49294/)).

Server-Sent Events injection emerged as a cross-language problem in 2026 with **three CVEs** in a single year. CVE-2026-35515 in NestJS showed that `SseStream._transform()` writes `message.type` and `message.id` into SSE output without removing CR/LF characters, enabling event splitting and XSS when clients render event data as HTML ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2026-35515)). CVE-2026-43968 in the Erlang cowlib library filtered `\n` in `id` and `event` fields but not bare `\r`, which the SSE spec treats as a line terminator, enabling forged events ([Erlang Ecosystem Foundation](https://cna.erlef.org/cves/CVE-2026-43968.html)). JLSEC-2026-619 in Julia's HTTP.jl wrote `event`, `id`, and `retry` verbatim without CR/LF sanitization ([OSV](https://osv.dev/vulnerability/JLSEC-2026-619)). The attack pattern is analogous to HTTP header injection but in the SSE protocol context, and the XSS impact depends entirely on whether the EventSource consumer inserts `event.data` into the DOM via `innerHTML`. gRPC-Web and tRPC returned no XSS-specific CVEs for 2024-2026, though tRPC's prototype pollution vulnerability (CVE-2025-68130 in `formDataToObject`) could theoretically chain with client-side rendering to achieve XSS ([Sonatype](https://guide.sonatype.com/vulnerability/CVE-2025-68130)).

## Authentication flows and API documentation pages serve as high-value XSS staging points

OAuth redirect_uri remains a significant XSS attack surface. CVE-2026-32235 in Backstage's auth backend demonstrated that crafted URIs can pass allowlist verification while resolving to attacker hosts, enabling authorization code theft ([Stack.watch](https://stack.watch/vuln/CVE-2026-32235/)). The better-auth library (pre-1.6.13) failed to validate the scheme of `redirect_uri` values registered by OIDC clients, allowing registration of `javascript:` redirect URIs that executed in the authorization server's origin when a consent page assigned the returned value to `window.location.href` ([SecureLayer7](https://securelayer7.net/lab/better-auth-stored-xss-javascript-redirect-uri-oidc-provider)). CVE-2025-66040 in Spotipy showed an unsanitized error parameter in the library's local OAuth callback server allowing JavaScript execution during authentication ([GitLab Advisory](https://advisories.gitlab.com/pkg/pypi/spotipy/CVE-2025-66040/)). The OAuth `state` parameter, designed for CSRF protection, becomes a reflected XSS vector when rendered in HTML without encoding, because developers assume it contains "their" data rather than attacker-controlled input ([Praetorian](https://www.praetorian.com/blog/attacking-and-defending-oauth-2/)). PKCE prevents authorization code interception in transit but does not protect against XSS on the callback page itself -- an XSS there can read the code from the URL before the legitimate client exchanges it ([Dev.to](https://dev.to/roxdavirox/oauth-20-redirecturi-open-redirect-and-pkce-observable-pre-conditions-before-exploitation-4646)).

SAML RelayState parameter XSS is the most accessible SAML-related XSS vector. CVE-2025-50055 in OpenVPN Access Server (CVSS 6.4) let a configured remote ACS endpoint inject script through the RelayState parameter ([CyberStrike](https://cyberstrike.io/cve/CVE-2025-50055)). CVE-2025-12101 in Citrix NetScaler demonstrated reflected XSS in RelayState at the `/cgi/logout` endpoint, exploitable via CSRF since the endpoint accepted POST requests with a valid SAMLResponse and modified RelayState ([SecPod](https://www.secpod.com/blog/relaystate-ruse-exploiting-reflected-xss-in-citrix-netscaler/)). SAML signature bypass vulnerabilities like CVE-2024-45409 (CVSS 10.0 in ruby-saml, affecting GitLab) chain with XSS when forged NameID values are rendered in user profiles without encoding ([ProjectDiscovery](https://projectdiscovery.io/blog/github-enterprise-saml-authentication-bypass)). JWT claims (name, email, profile URL) create a stored XSS variant where the token serves as the persistence mechanism: a compromised IdP or unsanitized self-registration flow stores malicious claim values that execute when rendered via `innerHTML` ([FlowFunds PR](https://github.com/Rithvik09/FlowFunds/pull/1)). The combination of JWT claim XSS and localStorage token storage creates a self-reinforcing attack: the XSS payload executes on render and steals the JWT from localStorage, enabling lateral movement ([Medium](https://medium.com/redteam/stealing-jwts-in-localstorage-via-xss-6048d91378a0)).

Swagger UI has the most documented XSS-to-token-theft chain in API documentation. Versions 3.14.1 through 3.38.0 contain a DOM-based XSS caused by an outdated bundled DOMPurify (2.2.2), exploitable by loading a malicious specification file through the `url` or `configURL` query parameters. Researchers reported **more than 60 instances** across bug bounty programs ([Vidoc Security Lab](https://blog.vidocsecurity.com/blog/hacking-swagger-ui-from-xss-to-account-takeovers)). The complete chain works as follows: a victim loads a crafted API spec in Swagger UI, the DOM XSS fires via DOMPurify bypass, the injected script reads the auth token from localStorage (where Swagger UI stores it), and the token is exfiltrated to the attacker ([PortSwigger Daily Swig](https://portswigger.net/daily-swig/widespread-swagger-ui-library-vulnerability-leads-to-dom-xss-attacks)). CVE-2024-45801 in DOMPurify itself (malicious nested HTML bypassing depth checking) compounds this risk for Swagger UI deployments bundling affected DOMPurify versions ([GovWay Advisory](https://govway.readthedocs.io/it/latest/vulnerability-management/securityAdvisory/2024/CVE-2024-45801.html)). Kong Insomnia's CVE-2025-1087 (CVSS 9.8) demonstrated that API client tools are equally dangerous: template injection in the desktop application before version 11.0.2 enabled remote code execution through malicious API responses, imports, or cookies ([Tenable](https://www.tenable.com/cve/CVE-2025-1087)).

## API gateways and proxies amplify XSS through smuggling, header injection, and CRLF attacks

HTTP request smuggling turns reflected XSS into a stored-like attack by poisoning the TCP connection so a subsequent user's response includes the attacker's XSS payload. The technique has evolved significantly: James Kettle's 2025 Black Hat talk introduced **"chunk-extension TE.TE"** exploiting how front-end and back-end servers handle extensions appended to chunk sizes, and the 2024 **"TE.0" dechunking exploit** targets servers that accept chunked encoding but mishandle zero-length chunks ([Black Hat USA 2025](https://i.blackhat.com/BH-USA-25/Presentations/US-25-Kettle-HTTP1-Must-Die-The-Desync-Endgame-Wednesday.pdf)). HTTP/2-to-HTTP/1.1 downgrade smuggling remains the most impactful variant because HTTP/2's binary framing makes the smuggled content invisible to HTTP/2-aware WAFs, while the downgraded HTTP/1.1 request carries the XSS payload to the backend. CVE-2025-57804 in the python-hyper h2 library confirmed this: HTTP/2 request splitting allowed smuggling attacks by injecting CRLF characters into headers that were valid in HTTP/2 binary framing but became injection vectors when downgraded ([GHSA-847f-9342-265h](https://github.com/python-hyper/h2/security/advisories/GHSA-847f-9342-265h)).

CRLF injection bridges header manipulation to full XSS: by injecting a double CRLF sequence, an attacker terminates the response headers and starts an entirely new response body they control ([SecureFlag](https://knowledge-base.secureflag.com/vulnerabilities/inadequate_input_validation/http_response_splitting_vulnerability.html)). The "FrontJacking" technique combines CRLF injection, HTTP request header injection, and XSS to exploit poorly configured reverse proxies in shared hosting environments ([The Hacker Recipes](https://www.thehacker.recipes/web/config/http-response-splitting)). API gateways that accept HTTP/2 from clients and communicate with backends over HTTP/1.1 -- a very common architecture -- must validate that HTTP/2 header values do not contain CR or LF before downgrading, yet whether major gateways (Kong, AWS API Gateway, Azure API Management) perform this validation is undocumented.

Nginx reverse proxy misconfigurations create XSS surfaces through **unsafe variable reflection**, where `$uri` and `$document_uri` contain the decoded/normalized URI and reflect decoded user input when used in return or rewrite directives ([DevSecOps Guides](https://blog.devsecopsguides.com/p/attacking-nginx)). The `add_header` directive in a child block completely overrides parent block headers -- if CSP is set in the server block but a location block adds its own `add_header`, all parent security headers are silently dropped ([HackTricks](https://book.hacktricks.xyz/network-services-pentesting/pentesting-web/nginx)). X-Forwarded-Host header injection is confirmed in production: a December 2024 Bugcrowd disclosure against NASA described X-Forwarded-Host manipulation leading to reflected XSS ([Bugcrowd](https://bugcrowd.com/disclosures/3f102232-685e-4f53-ae90-1a1ba2392491/host-header-injection-open-redirection-leading-to-cross-site-scripting-xss)). CVE-2025-48865 in Fabio and CVE-2025-64484 in OAuth2-proxy introduced a newer technique: underscore-hyphen normalization differences where proxies treat `X_Forwarded_Host` and `X-Forwarded-Host` differently, allowing header injection that the proxy does not strip but the backend trusts ([Security Boulevard](https://securityboulevard.com/2026/03/when-proxies-become-attack-vectors-through-header-injection/)).

Kong API Gateway's request smuggling flaw (CVE-2026-6338) in its HTTP/1.1 parsing pipeline could chain with backend XSS ([OpenCVE](https://app.opencve.io/cve/?product=kong_enterprise_gateway&vendor=kong)), while its authentication bypass (CVE-2026-29413, CVSS 9.8) and exposed Admin API create conditions where an attacker could install custom plugins injecting script content into every proxied response ([Acunetix](https://www.acunetix.com/vulnerabilities/web/unprotected-kong-gateway-admin-api-interface/)). AWS API Gateway's Lambda proxy integration passes through whatever the Lambda function returns, so any XSS in the Lambda response reaches the client unmodified -- functionally equivalent to a direct-to-backend connection for XSS purposes ([AWS Documentation](https://docs.aws.amazon.com/lambda/latest/dg/services-apigateway.html)).

## Parameter pollution and encoding attacks systematically defeat WAF XSS protection

The WAFFLED methodology from Northeastern and Dartmouth (March 2025) held the attack payload constant and mutated only the HTTP structure, producing **557 JSON bypasses, 351 multipart bypasses, and 299 XML bypasses** across AWS WAF, Azure WAF, Google Cloud Armor, Cloudflare, and ModSecurity. More than **90% of tested applications accepted both `application/x-www-form-urlencoded` and `multipart/form-data` interchangeably**, widening the attack surface for content-type switching ([WAFFLED Paper](https://arxiv.org/html/2503.10846v1)). The researchers released HTTP-Normalizer, a proxy tool that validates HTTP requests against RFC standards as a mitigation, and all affected vendors acknowledged the vulnerabilities ([Cryptika](https://www.cryptika.com/new-waffled-attack-exploits-aws-azure-cloud-armor-cloudflare-and-modsecurity-wafs/)).

HTTP parameter pollution (HPP) exploits the divergence between how WAFs and backend frameworks handle duplicate parameters. ASP.NET's `HttpUtility.ParseQueryString()` concatenates duplicate values with commas, and combined with JavaScript's comma operator, this enables XSS payloads split across multiple parameters to reassemble on the backend. Bruno Mendes' August 2025 research tested 17 WAF configurations including AWS, Google Cloud, Azure, and Cloudflare; **only 3 blocked the attack** ([CyberSecurityNews](https://cybersecuritynews.com/wafs-protection-bypassed/)). Node.js Express creates arrays from duplicate params, opening a distinct type-confusion surface when an array is coerced to string. PHP takes the last parameter value, Apache Tomcat uses the first -- when a WAF inspects one value and the backend renders another, the filter check and execution context diverge ([Medium](https://medium.com/@pavankumarck684/http-parameter-pollution-hpp-78197aef60b7)).

Body-size limits are a systemic WAF weakness. MDSec found Cloudflare ignoring requests over **131,072 bytes (128 KiB)** on a public-sector API ([MDSec](https://www.mdsec.co.uk/2024/10/when-wafs-go-awry-common-detection-evasion-techniques-for-web-application-firewalls/)). AWS WAF inspects only the **first 8 KB** of the request body for Application Load Balancer and AppSync, allowing attackers to pad requests with junk data to push XSS payloads outside this inspection window ([MDSec](https://www.mdsec.co.uk/2024/10/when-wafs-go-awry-common-detection-evasion-techniques-for-web-application-firewalls/)). CVE-2026-44982 in CrowdSec AppSec demonstrated that even in 2026, switching one header from Content-Length to Transfer-Encoding: chunked changed the response from 403 Forbidden to 200 OK, bypassing body inspection entirely ([CVE-2026-44982 Advisory](https://mmartin.me/blog/crowdsec-appsec-bypass-cve-2026-44982)).

ModSecurity CRS suffered a cluster of 2026 CVEs affecting core transformations. CVE-2026-52761 showed that the `t:utf8toUnicode` transformation produces incorrect output on 32-bit systems, allowing full-width UTF-8 XSS payloads to slip past rules ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2026-52761)). CVE-2026-21876 (CVSS 9.3) revealed that CRS rule 922110 validates only the last part of a multipart request for UTF-7 and UTF-16 charsets, allowing earlier parts to carry malicious charsets ([eSecurity Planet](https://www.esecurityplanet.com/threats/owasp-crs-flaw-lets-encoded-attacks-slip-past-wafs/)). Unicode normalization bypasses exploit NFKC/NFKD differences between WAFs and backends: fullwidth characters pass WAF inspection and are normalized to ASCII equivalents by backend frameworks, enabling XSS execution. The defense is straightforward -- normalize before filtering -- but WAFs that apply NFKC normalization before signature matching remain the exception ([Jorge Lajara](https://jlajara.gitlab.io/Bypass_WAF_Unicode)).

## Webhooks, file uploads, and microservice boundaries propagate XSS across trust domains

Webhook stored XSS follows a canonical pattern demonstrated by CVE-2026-11855 in the Simple Membership WordPress plugin (CVSS 8.8): Stripe webhook payloads are stored and rendered in admin notices without HTML escaping or signature verification ([OpenCVE](https://app.opencve.io/cve/CVE-2026-11855)). The vulnerability surface is in third-party applications that receive and display webhook data, not in the webhook providers themselves -- Stripe, GitHub, and Slack's own dashboard interfaces appear to properly sanitize webhook data. The pattern extends to any SaaS webhook that includes user-controlled fields (customer names, message bodies, product descriptions), where the receiving application renders them without sanitization.

SVG upload XSS is the most common file-type-specific XSS vector in 2025, with at least **six CVEs across different products**. CVE-2025-66512 in Nextcloud demonstrated that when SVGs were viewed outside the application via direct URL, the browser did not enforce Nextcloud's CSP, allowing embedded scripts to execute ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-66512/)). CVE-2025-65516 in Seafile's Golang file server showed that attackers could share a public link to deliver SVG XSS payloads without needing the victim's session ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-65516/)). CVE-2025-9698 in Plus Addons for Elementor allowed an Author-level user to upload an SVG that stole authentication cookies, performed REST API actions as admin, and installed backdoor plugins when an administrator previewed it ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-9698/)). Content-Type confusion through file uploads was further demonstrated by CVE-2026-32728 and CVE-2026-61448, both in Parse Server, where malformed Content-Type parameters and missing XML extension blocklist entries bypassed MIME checks ([Vulners](https://vulners.com/cvelist/CVELIST:CVE-2026-32728)). The Netty multipart encoder (CVE-2026-59921, CVSS 8.1) showed that unvalidated filenames containing CRLF characters can inject extra MIME headers with XSS as a possible impact ([TuxCare](https://tuxcare.com/cve-tracker/cve/details/cve-2026-59921/)).

Inter-service stored XSS in microservice architectures is a recognized but underdocumented architectural risk. The pattern occurs when Service A stores unsanitized data (because it never renders HTML) and Service B renders it (because it trusts data from the "internal" database). Neither service owns output encoding. Mitigation guidance states that every service rendering HTML should "never trust HTML coming from other microservices" and use "shared encoding and sanitizing libraries" ([Design Gurus](https://www.designgurus.io/answers/detail/how-do-you-mitigate-ssrfcsrfxss-across-a-microservices-stack)). Event-driven architectures add another layer: CVE-2026-49098 in Apache Camel's Kafka component demonstrated that header injection in event systems lets forged messages reach unintended topics ([CraftedSignal Feed](https://feed.craftedsignal.io/tags/kafka/feed.json)). Kafka admin UIs (kafka-ui, AKHQ, Kafdrop) that render message keys, values, and headers in web interfaces are direct XSS targets when topics contain messages with HTML/JavaScript in the value. Service mesh tracing header reflection (X-Request-ID, traceparent, B3 headers) represents an unstudied XSS surface: no CVEs or advisories were found for Istio, Envoy, or Linkerd addressing this vector, though Envoy's default behavior of overwriting X-Request-ID with its own UUID would mitigate the attack in default configuration.

XSS in API contexts achieves maximum impact through chaining. The most common chains in 2024-2026 include: **XSS to API token theft to privilege escalation** (Grafana CVE-2025-6023 demonstrated stored XSS in a dashboard leading to API token theft ([CHS.us](https://chs.us/guides/xss/))); **mass assignment to stored XSS at scale** (a major chatbot platform's unsafe JSON merge affected approximately 500 customer instances ([Medium](https://medium.com/@melodicbook/how-mass-assignment-led-to-stored-xss-and-a-csp-bypass-in-a-major-chatbot-platform-3c6569d7c9e9))); and **XSS to RCE** (Langflow CVE-2025-34291 showed account takeover where XSS read a non-HttpOnly token cookie ([Obsidian Security](https://www.obsidiansecurity.com/blog/cve-2025-34291-critical-account-takeover-and-rce-vulnerability-in-the-langflow-ai-agent-workflow-platform))).

## Conclusion

The research reveals a structural problem in API security: the multi-layered processing pipeline inherent to API architectures -- API gateway, WAF, reverse proxy, service mesh sidecar, application framework, template engine -- creates encoding and parsing mismatches at every boundary, and each mismatch is a potential XSS injection point. WAFs are provably insufficient as primary protection for API traffic, with bypass rates exceeding 80% for parameter pollution and parser-discrepancy attacks across major vendors. The defense must shift to the rendering layer: applications consuming API responses must treat all data as untrusted regardless of whether it came from an "internal" service, a webhook, or a trusted IdP. The emerging preventive stack -- **Trusted Types** (now at Baseline browser support with Firefox 148, Chrome 83+, and Safari 26+), **CSP with nonce + strict-dynamic**, and **context-aware output encoding** at the final rendering point -- addresses API XSS more effectively than any gateway-level control. For detection, schema-aware API fuzzing (combining tools like RESTler or Schemathesis with XSS payload libraries) and RASP agents that operate at the code-execution level offer lower false-positive rates than WAF signatures, though Go and Rust ecosystems still lack mature RASP tooling. The least-studied attack surfaces -- service mesh tracing header reflection, GraphQL subscription message XSS, gRPC-Web JSON mode transcoding, and presigned URL abuse for origin-level script execution -- represent gaps where future vulnerabilities are most likely to emerge.
