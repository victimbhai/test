# Advanced API attacks bypass traditional defenses through protocol-layer exploitation

The most critical and commonly missed API security vulnerabilities in 2025-2026 exploit **structural mismatches between components in multi-layer architectures** -- gateway vs. backend path normalization, HTTP/2 vs. HTTP/1.1 framing, WAF vs. application JSON parsing, and CDN vs. origin URL interpretation. Traditional API security testing, anchored to the OWASP API Security Top 10, catches authorization and injection flaws at the application layer but systematically misses attacks that operate at the protocol, infrastructure, and business-logic layers. This report synthesizes research across **22 attack categories** that fall outside conventional API security coverage: API gateway bypass, service mesh mTLS subversion, gRPC reflection and protobuf deserialization, HTTP/2-3 smuggling, OAuth device-code phishing and PKCE downgrade, WebSocket hijacking and state confusion, WAF parser-disagreement bypass, web cache deception and poisoning, serverless event injection and credential theft, AI/LLM prompt injection and model extraction, MCP tool poisoning, supply chain compromise of API middleware, mobile API instrumentation attacks, business logic race conditions and price manipulation, advanced CORS exploitation, webhook SSRF via DNS rebinding, shadow API version downgrade, SSTI through JSON parameters, file upload polyglot attacks, insecure deserialization gadget chains, DNS rebinding against internal APIs, and Kubernetes API server exploitation. The common thread is that **every trust boundary where one component's output becomes another component's input, with different parsing or normalization, creates an exploitable gap**. Defending against these attacks requires canonicalization at the outermost layer, protocol-aware inspection, server-side state enforcement, and zero-trust architecture that validates every request regardless of network origin.

## API gateway path normalization creates the most productive bypass class

API gateways are routinely bypassed through path normalization mismatches between the gateway's authorization layer and the backend application. The RFC leaves URL-encoded path decoding order to each implementation, and **six CVEs across APISIX, Traefik, AWS API Gateway, Spring MVC, ModSecurity, and Apache httpd all share this flaw class** where the ACL evaluates the path at a different normalization state than the backend serves ([DEV Community](https://dev.to/roxdavirox/api-gateway-path-normalization-bypass-when-haproxy-sees-admin-and-your-app-sees-admin-3heh)). A researcher discovered that `GET /v1/accounts` returned 401 while `GET /v1/accounts/` returned 200 OK with full account data on an AWS HTTP API endpoint, earning a **$12,000 bounty** -- the trailing slash bypassed the Lambda authorizer because the greedy route match dropped the auth context ([InfoQ](https://www.infoq.com/news/2026/06/aws-api-gateway-auth-bypass/)). Double slashes (`//admin/config`), semicolons (`/admin;anything` where Tomcat strips the parameter segment), double URL encoding (`/%2561dmin`), dot segments (`/./admin`), and Unicode normalization (`/adm%C4%B1n`) all exploit the same structural flaw ([Medium](https://medium.com/@dipanshuchhanikar/bypassing-authentication-in-a-major-api-gateway-a-path-normalization-story-5f1bea6d3f08)).

Traditional testing misses this because scanners probe the canonical path, not its many alternative representations. Reproduction requires systematic fuzzing: identify a protected endpoint returning 401/403, then test every normalization variant with Burp Suite Intruder or Nuclei templates and compare response codes and bodies against the canonical path. Header injection compounds the problem -- `X-Original-URL`, `X-Rewrite-URL`, and `X-HTTP-Method-Override` headers can override the path or method the gateway authorized, and `X-Forwarded-For` spoofing bypasses IP-based ACLs ([HackTricks](https://hacktricks.wiki/en/pentesting-web/proxy-waf-protections-bypass.html)). Kong Gateway's **CVE-2026-6338** confirms even mature gateways remain susceptible to HTTP request smuggling through parsing discrepancies with untrusted HTTP/1.1 traffic ([stack.watch](https://stack.watch/product/konghq/)), while **CVE-2021-27306** demonstrated JWT plugin authentication bypass. The defense is to canonicalize the request path -- resolve dot segments, normalize encoding, strip semicolons -- before evaluating authorization policies, and to strip or reject routing-override headers at the gateway layer.

## HTTP/2-3 smuggling and h2c upgrade bypass infrastructure security controls

HTTP/2 introduces request smuggling vectors that traditional HTTP/1.1 testing never encounters. **H2C smuggling** abuses the `Upgrade: h2c` mechanism to switch a connection to cleartext HTTP/2 -- when a reverse proxy forwards the upgrade without understanding it, the proxy loses content awareness and subsequent HTTP/2 requests bypass routing rules, WAF inspection, and authentication checks entirely ([Bishop Fox](https://bishopfox.com/blog/h2c-smuggling-request)). Assetnote found authentication, routing, and WAF bypasses across cloud providers using this technique, and PortSwigger ranked it the top web hacking technique of 2020 ([Assetnote](https://blog.assetnote.io/2021/03/18/h2c-smuggling)). The h2cSmuggler tool automates the attack, and testing is straightforward: `python3 h2csmuggler.py -x https://target/` reveals whether the proxy forwards h2c upgrades.

**H2.CL and H2.TE desync attacks** target the HTTP/2-to-HTTP/1.1 downgrade boundary that exists in most production architectures. James Kettle's PortSwigger research documents these: in H2.CL, the attacker sends an HTTP/2 request with a `content-length` header that disagrees with the actual DATA frame length -- the front-end uses the DATA frame while the backend uses Content-Length, creating a message boundary mismatch. In H2.TE, injecting a `transfer-encoding: chunked` header into the HTTP/2 request succeeds because HTTP/2 ignores it, but after downgrade to HTTP/1.1 the backend processes it ([PortSwigger](https://portswigger.net/research/http2)). **CVE-2023-44487 (HTTP/2 Rapid Reset)** remains the most impactful protocol-level attack, exploited as a zero-day from August through October 2023 -- Google reported **398 million requests per second**, Cloudflare 205 million rps, and AWS 155 million rps. The flaw impacts every web server implementing HTTP/2 and has **448 public PoC repositories** ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2023-44487/); [Anvilogic](https://www.anvilogic.com/threat-reports/http2-rapid-reset-ddos-cve-2023)).

QUIC/HTTP/3 introduces new evasion surfaces. **CVE-2026-48743** is an HTTP/3-to-HTTP/1 translation-boundary smuggling flaw in Envoy (CVSS 7.5 High) that lets unauthenticated attackers reach backend paths Envoy had denied ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2026-48743)). QUIC's connection migration fundamentally breaks IP-based rate limiters, IDS/IPS, and load balancers by allowing clients to change source IP/port mid-connection ([IEEE Xplore](https://ieeexplore.ieee.org/document/10427406)). A 2025 study found servers often do not enforce QUIC's anti-DoS 3x amplification limit ([UCLouvain](https://research.dial.uclouvain.be/handle/2078.5/256415)). Defense requires limiting `SETTINGS_MAX_CONCURRENT_STREAMS`, rate-limiting RST_STREAM frames, blocking `Upgrade: h2c` headers at the proxy, and reconstructing HTTP/1.1 requests from parsed HTTP/2 components rather than forwarding raw bytes ([arXiv](https://arxiv.org/pdf/2510.09952); [Microsoft MSRC](https://msrc.microsoft.com/update-guide/vulnerability/CVE-2023-44487)).

## Service mesh mTLS guarantees erode through PERMISSIVE defaults and sidecar manipulation

Service meshes promise zero-trust networking through mutual TLS, but Istio's **default mTLS mode is PERMISSIVE** -- accepting both mTLS and plaintext traffic -- and its traffic interception relies on iptables rules that an attacker with `NET_ADMIN` or `CAP_NET_RAW` in a compromised pod can modify to bypass the sidecar entirely ([AquiLAX](https://aquilax.ai/blog/service-mesh-istio-mtls-bypass)). The 2024-2026 Istio security advisories reveal a pattern of header-handling flaws: **CVE-2024-45806** allows external sources to inject `x-envoy-*` internal headers through the ingress gateway, manipulating routing and authorization ([Istio Security 2024-006](https://istio.io/latest/news/security/istio-security-2024-006/)). **ISTIO-SECURITY-2026-006** documents a fail-open condition where `BackendTLSPolicy` falls back to plaintext when its CA reference is unresolved ([Istio Security 2026-006](https://istio.io/latest/news/security/istio-security-2026-006/)). **CVE-2026-31838** allows authorization policy bypass through crafted header value arrangements, and **CVE-2026-39350** reveals that dots in `serviceAccounts` fields of AuthorizationPolicy are incorrectly treated as regex wildcards instead of literal dots, matching unintended accounts.

Container sidecar injection attacks exploit Kubernetes pod-creation privileges to inject malicious containers alongside workloads. **CVE-2026-23766** in Istio allowed argument injection through the `traffic.sidecar.istio.io/excludeInterfaces` annotation, enabling users with pod-creation rights to alter traffic flow in the pod's network namespace ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-23766/)). An injected sidecar can read the pod's service account token from the shared `/var/run/secrets/kubernetes.io/serviceaccount` directory and impersonate the legitimate service to the mesh control plane ([InstaTunnel](https://scour.ing/@abnv/p/https://instatunnel.my/blog/the-sidecar-siphon-exploiting-identity-leaks-in-service-mesh-architectures)). Reproduction starts with checking `PeerAuthentication` for PERMISSIVE mode (`kubectl get peerauthentication --all-namespaces`), identifying pods with `NET_ADMIN` capabilities, and testing `x-envoy-*` header injection from outside the mesh. Defense requires STRICT mTLS mode, stripping `x-envoy-*` headers at the ingress, and dropping `NET_ADMIN` and `CAP_NET_RAW` from all workload containers.

## gRPC reflection and protobuf deserialization enable schema-driven exploitation

gRPC server reflection left enabled in production exposes the entire API surface to unauthenticated discovery. Running `grpcurl -plaintext target:port list` reveals all registered services; `grpcurl -plaintext target:port describe <service>` maps every method and message type. Combined with missing per-RPC authorization on streaming methods, this creates a significant attack surface that conventional REST-focused scanners never test ([StackHawk](https://www.stackhawk.com/blog/grpc-api-security-best-practices)). Protobuf deserialization vulnerabilities range from DoS through stack exhaustion (**CVE-2024-7254** in protobuf-java, where nested groups exhaust the stack) to **RCE through schema poisoning -- CVE-2026-41242 in protobuf.js** (52M+ downloads), where an attacker who can influence a protobuf schema achieves code execution on the first decode ([CSA](https://labs.cloudsecurityalliance.org/wp-content/uploads/2026/04/CSA_research_note_protobufjs-rce-cve-2026-41242_20260420-csa-styled-3.pdf)). **CVE-2024-7246** introduces HPACK table poisoning: a gRPC client communicating through an HTTP/2 proxy poisons the HPACK dynamic table, causing corrupted or attacker-controlled header values to reach the backend ([Tenable](https://tenable.com/cve/CVE-2024-7246)).

gRPC-Web proxies create a blind spot because they translate between HTTP/1.1 browser requests and HTTP/2 gRPC backend calls. The gRPC-Web protocol uses base64-encoded protobuf in HTTP/1.1 POST bodies, which most WAFs and API gateways cannot inspect. Bidirectional streaming RPCs require different rate-limiting approaches than unary RPCs -- standard API rate limiters that count HTTP requests miss the unbounded messages within a single long-lived stream, and a stream that never terminates can hold server resources indefinitely if no timeout is enforced. Defense requires disabling reflection in production, enforcing per-RPC authorization on all methods including streaming RPCs, setting maximum message sizes and stream timeouts, and pinning protobuf library versions rather than trusting reflection-supplied schemas for runtime code generation. Tools for gRPC security testing include `grpcurl`, `grpcui`, `ghz` for load testing, and `mitmproxy` with the gRPC plugin for traffic inspection.

## OAuth device code phishing and PKCE downgrade undermine modern authentication

Device code phishing escalated from a niche red-team technique to a widespread attack vector in 2025, with both state-aligned and financially motivated groups targeting Microsoft 365 using toolkits such as SquarePhish2, Graphish, and Kali365 ([Proofpoint](https://www.proofpoint.com/us/blog/threat-insight/access-granted-phishing-device-code-authorization-account-takeover)). The attack is uniquely effective because the victim interacts with the **legitimate IdP page** -- there is no phishing page to detect. The attacker initiates a device authorization request to the target's `/devicecode` endpoint, receives a `device_code` and `user_code`, delivers the code to the victim via email, Teams, or voice call, and polls the `/token` endpoint until the victim authenticates. Salesforce removed the OAuth device flow entirely in September 2025, treating the feature as a liability ([AppOmni](https://appomni.com/blog/device-code-phishing-saas/)).

**PKCE downgrade** remains actively exploited. **CVE-2025-4144** in Cloudflare's `workers-oauth-provider` (used by the MCP framework's OAuth implementation) allowed PKCE checks to be skipped ([GitHub Advisory GHSA-qgp8-v765-qxx9](https://github.com/cloudflare/workers-oauth-provider/security/advisories/GHSA-qgp8-v765-qxx9)), and **CVE-2023-48228** and **CVE-2024-23647** in authentik demonstrated the same pattern -- the authorization server accepted PKCE in one request and its absence in the next. The attack strips `code_challenge` from the authorization request; if the server treats PKCE as optional, the code is issued without verifier binding, nullifying protection against interception. RFC 9700 now mandates rejection of mismatched PKCE presence, and OAuth 2.1 makes PKCE mandatory, but adoption is not universal ([RFC 9700](https://www.rfc-editor.org/info/rfc9700/)).

JWT key reference injection continues producing bounties. Directory traversal through the `kid` parameter (e.g., `../../dev/null` forcing verification against an empty secret) and SQL injection in `kid` (returning attacker-chosen key material) both exploit the bridge between JWT verification and injection-vulnerability territory ([DEV Community](https://dev.to/roxdavirox/jwt-kid-parameter-attacks-sql-injection-and-path-traversal-via-key-id-5607)). The `jku` header enables SSRF-to-key-spoofing: the attacker points it to their own JWK Set URL, and the server fetches the attacker's public key for verification. **CVE-2026-48522** reportedly shows PyJWT's `PyJWKClient` accepting `file://`, `ftp://`, and `data:` URIs in `jku` ([DEV Community](https://dev.to/roxdavirox/jwt-key-reference-injection-the-attack-class-that-wins-bounties-while-guides-miss-it-421)). The `jwk` embedded-key injection (**CVE-2018-0114** in node-jose, CVSS 8.1) allowed the library to trust the JWK in the token header for verification. Defense requires server-side allowlists for JWKS URIs, treating `kid` as an opaque identifier never used in filesystem paths or SQL, and explicitly configuring the expected algorithm.

## WebSocket hijacking exploits default-insecure frameworks and transport-layer auth gaps

Cross-Site WebSocket Hijacking (CSWSH) remains viable because **four of five dominant WebSocket frameworks leave Origin validation disabled by default**, making applications vulnerable out of the box ([DEV Community](https://dev.to/rxkov/cswsh-four-major-websocket-frameworks-default-to-vulnerable-while-attackers-get-a-bidirectional-hj8)). A malicious page opens a WebSocket to the victim's application, the browser attaches the victim's cookies, and without Origin validation, the attacker gains bidirectional access to the authenticated session. **CVE-2024-26135** (MeshCentral) allowed leaking configuration data and generating login tokens via CSWSH ([GitHub Advisory](https://github.com/advisories/GHSA-cp68-qrhr-g9h8)); **CVE-2024-51775** (Apache Zeppelin) allowed any remote attacker to read paragraph content; and Mailpit's `CheckOrigin` function was set to always return true ([Mailpit Advisory](https://github.com/axllent/mailpit/security/advisories/GHSA-524m-q5m7-79mm)). SameSite=Lax has a two-minute grace period after cookie issuance during which cookies are sent with cross-site POST requests, and it does not block same-site requests from sibling subdomains ([Dozzle Advisory](https://github.com/amir20/dozzle/security/advisories/GHSA-j643-x8pv-8m67)). Reproduction: send a WebSocket upgrade with `Origin: https://attacker.com` -- if the server responds with `101 Switching Protocols`, it is exploitable.

GraphQL subscription endpoints compound the WebSocket problem. **CVE-2026-5423** (Neo4j `@neo4j/graphql`, CVSS 8.2) demonstrates that the subscriptions transport accepted `connectionParams.jwt` without verifying the signature, allowing unauthenticated clients to forge claims trusted by authorization directives ([GHSA-fcpg-3fw5-vc65](https://github.com/neo4j/graphql/security/advisories/GHSA-fcpg-3fw5-vc65)). Strawberry GraphQL's legacy `graphql-ws` handler (**GHSA-vpwc-v33q-mq89**) accepted subscription messages without completing `connection_init`, skipping the authentication hook ([Strawberry Advisory](https://github.com/strawberry-graphql/strawberry/security/advisories/GHSA-vpwc-v33q-mq89)). The root cause is architectural: WebSocket connections establish through a protocol upgrade that bypasses HTTP middleware stacks. Message-layer attacks add injection risks -- **CVE-2026-54466** (websocket-driver via SockJS) causes parser state confusion through integer overflow on the message length counter, silently corrupting message boundaries ([GitHub Issue](https://github.com/smogon/pokemon-showdown/issues/12268)), and **CVE-2026-47072** (Netty) enables handshake smuggling by accepting WebSocket upgrades without required headers ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-47072)).

## WAF bypass exploits parser disagreements between inspection layer and backend

WAF bypasses exploit structural disagreements in how WAFs and backends parse HTTP, JSON, SQL, and URL paths. Claroty Team82's **"JS-ON: Security-OFF" research** found that appending JSON syntax to SQL injection payloads bypassed WAFs from **Palo Alto Networks, AWS, Cloudflare, F5, and Imperva** because these WAFs did not parse JSON in SQL contexts ([Claroty](https://claroty.com/team82/research/js-on-security-off-abusing-json-based-sql-to-bypass-waf)). The 2025 WAFFLED research identified **1,207 WAF bypass variants** across Azure, Cloudflare, Google Cloud Armor, AWS WAF, and ModSecurity, classified as HTTP request smuggling -- the core problem being parser disagreement between WAF and backend on how to interpret HTTP messages ([Cryptika](https://www.cryptika.com/new-waffled-attack-exploits-aws-azure-cloud-armor-cloudflare-and-modsecurity-wafs/)). Content-Type switching (sending JSON payloads with `text/plain` Content-Type) causes WAFs to skip JSON inspection while the backend still parses JSON ([MDSec](https://www.mdsec.co.uk/2024/10/when-wafs-go-awry-common-detection-evasion-techniques-for-web-application-firewalls/)). Payload padding exploits WAF body-size inspection limits: some WAFs inspect only the first 8-16KB, so junk keys before the malicious payload push it past the inspection window ([JSMon](https://blogs.jsmon.sh/how-to-bypass-wafs-using-payload-padding-and-inspection-limits/)).

Web cache deception exploits URL interpretation mismatches between CDNs and origin servers. When a CDN treats `/api/user/profile/image.css` as a static cacheable resource while the origin serves the authenticated `/api/user/profile` response, the attacker tricks the cache into storing private API responses accessible to anyone ([Black Hat 2017](https://blackhat.com/docs/us-17/wednesday/us-17-Gil-Web-Cache-Deception-Attack-wp.pdf); [GBHackers](https://gbhackers.com/new-cache-deception-attack-exploits/)). Cache key normalization attacks exploit different URL parsing between CDNs and origins -- PortSwigger's "Gotta Cache 'Em All" research found that Cloudflare, Google Cloud, and Fastly did not normalize paths in cache keys while CloudFront, Azure, and Imperva did, and unkeyed headers like `X-Forwarded-Host` become classic poisoning vectors ([PortSwigger](https://portswigger.net/research/gotta-cache-em-all)). The WAFFLED researchers released HTTP-Normalizer, an open-source proxy that re-parses and reserializes HTTP messages to eliminate parser ambiguity as a defense.

## Rate limiting bypasses exploit IP header spoofing and GraphQL batching

API rate limiting bypasses exploit the gap between what the limiter counts and what reaches the backend. The most productive class is IP header spoofing -- **CVE-2026-107271** (Gophish), **CVE-2026-84476** (AVideo, CVSS 8.7), **CVE-2026-54738** (Lemmy), **CVE-2026-64619** (FileCodeBox, CVSS 7.5), **CVE-2026-24000** (Fleet), and **CVE-2026-27981** (HomeBox) all demonstrate applications trusting client-supplied `X-Forwarded-For` or `X-Real-IP` headers without verifying they came through a trusted proxy ([OpenCVE](https://app.opencve.io/cve/CVE-2026-107271); [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-54738/); [Lutra Security](https://fieldguide.lutrasecurity.com/CVE-2026-27981)). Spoofable headers include `X-Forwarded-For`, `X-Real-IP`, `X-Originating-IP`, `X-Client-IP`, `True-Client-IP`, `CF-Connecting-IP`, and others ([SecureLayer7](https://securelayer7.net/learn/api-security/rate-limit-bypass)). GraphQL batching compounds the problem -- array batching sends a JSON array of operations counted as one HTTP request while executing many, and alias batching calls the same field multiple times within one operation, each with different arguments. Checkmarx demonstrated **100 login mutations with different passwords in a single request** ([Checkmarx](https://checkmarx.com/?p=80723)). Defense requires counting operations rather than requests, implementing per-operation cost analysis, and using account-based or session-based rate limiting instead of IP-only counting.

## Serverless event injection targets non-HTTP triggers that developers trust blindly

Event injection is the signature serverless vulnerability: untrusted data from S3, SNS, SQS, DynamoDB Streams, and CloudWatch Events reaches Lambda function code without validation because developers treat the event payload as trusted internal data ([JSMon](https://blogs.jsmon.sh/aws-lambda-security-exploiting-event-injection-and-credential-theft/)). An S3 object key like `'; DROP TABLE users; --` triggers SQL injection in a function that uses the key in a query. SNS/SQS messages are attacker-controlled when the topic accepts external publishers. DynamoDB Streams can be poisoned if another compromised function writes to the table. Blueinfy documented blind Lambda event injection techniques using timing and error-message side channels when the function has no internet access ([Blueinfy](https://blog.blueinfy.com/2018/10/blind-lambda-event-injections-without_24.html)). Lambda functions do not use the EC2 metadata service -- IAM credentials are injected as environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`), so credential theft requires code execution or environment variable leakage through error responses rather than SSRF to 169.254.169.254 ([DarkReading](https://www.darkreading.com/cloud-security/securing-serverless-attacking-an-aws-account-via-a-lambda-function)).

Lambda function URLs with `AUTH_TYPE=NONE` are publicly accessible with no authentication, no throttling, and no WAF integration. Wiz reports that attackers find these URLs through passive DNS matching `*.lambda-url.*.on.aws` ([Wiz](https://www.wiz.io/blog/securing-aws-lambda-function-urls)). Denial-of-wallet attacks exploit the pay-per-use billing model by triggering excessive invocations -- recursive trigger chains (Lambda writes to S3, triggering another Lambda, writing to DynamoDB, triggering another) create amplification where a single request generates thousands of downstream invocations. The `/tmp` directory persists across warm invocations of the same container (512MB, configurable to 10GB), enabling persistence after code execution -- a payload written to `/tmp` survives subsequent invocations, and data from previous requests can be read. Defense requires using Secrets Manager instead of environment variables, clearing `/tmp` at invocation start, placing CloudFront or API Gateway with throttling in front of Lambda URLs, and setting reserved concurrency limits.

## AI/LLM APIs face prompt injection, model extraction, and MCP tool poisoning

Prompt injection remains the number one risk in the OWASP LLM Top 10 2025. **CVE-2025-32711 (EchoLeak)** demonstrated zero-click indirect prompt injection against Microsoft 365 Copilot -- a crafted email containing hidden instructions triggered data exfiltration when Copilot processed it, requiring emergency patches ([arXiv](https://arxiv.org/html/2509.10540v1); [Prem.AI](https://blog.premai.io/prompt-injection-attacks-in-2025-vulnerabilities-exploits-and-how-to-defend/)). **CVE-2024-8309** (LangChain GraphCypherQAChain) enabled full Neo4j database compromise through Cypher injection via LLM prompts ([Keysight](https://www.keysight.com/blogs/en/tech/nwvs/2025/08/29/cve-2024-8309)). Model extraction via API is proven at production scale: Carlini et al. (2024) extracted the embedding projection layer of OpenAI models for approximately **$2,000 in API costs**, and Anthropic disclosed that three Chinese AI companies collectively issued **more than 16.55 million queries to Claude API** through approximately 24,000 fraudulent accounts for distillation-based extraction ([CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-llm-model-extraction-cloud-scale-20260308/)).

The Model Context Protocol (MCP) ecosystem introduced a new attack surface. Invariant Labs discovered tool poisoning where a malicious MCP server embeds hidden instructions in tool descriptions, overriding instructions from trusted servers and exfiltrating data across connected servers ([Invariant Labs](https://invariantlabs.ai/blog/mcp-security-notification-tool-poisoning-attacks)). **CVE-2025-6514** (mcp-remote, CVSS 9.6) enabled RCE through unsanitized OAuth metadata, and **CVE-2025-49596** (Anthropic MCP Inspector, CVSS 9.4) allowed remote code execution in the inspection tool ([AuthZed](https://authzed.com/blog/timeline-mcp-breaches)). An email MCP supply chain attack in September 2025 pushed an update that silently BCC'd every agent-sent email to an attacker-controlled domain. LLM framework SDKs propagate vulnerabilities at scale: LangChain has accumulated **12+ CVEs** across components including RCE, SSRF, and Cypher injection, while LlamaIndex's **CVE-2025-1793** (SQL injection in vector store integrations, CVSS 9.8) affects modern AI infrastructure ([Flatt Security](https://dev.to/gmo-flatt-security-inc/llm-framework-vulns-exposed-learnings-from-cves-2j48)).

## Supply chain attacks compromise API middleware, SDKs, and CI/CD pipelines

The LiteLLM AI gateway attack chain is the most severe 2025-2026 supply chain example. **CVE-2026-42271** (command injection via MCP server test endpoints, actively exploited, added to CISA KEV) chains with **CVE-2026-48710** (host header validation flaw, CVSS 10.0 by Horizon3.ai) to achieve unauthenticated RCE. **CVE-2026-42208** (pre-auth SQL injection, CVSS 9.3, actively exploited) exposes stored API keys for every connected LLM provider. Most critically, **CVE-2026-33634** documents how the threat group TeamPCP compromised LiteLLM's CI/CD pipeline through the Trivy scanner, publishing malicious PyPI versions 1.82.7 and 1.82.8 ([CSA Labs](https://labs.cloudsecurityalliance.org/research/csa-research-note-litellm-ai-gateway-attack-chain-20260617-c/)). This mirrors the broader supply chain pattern: the Solana web3.js npm library was compromised through phished maintainer credentials in December 2024, the Shai-Hulud npm worm propagated through 18+ packages in September 2025, and the tj-actions/changed-files GitHub Action was modified to leak CI/CD secrets in March 2025 ([SOCRadar](https://socradar.io/blog/top-10-supply-chain-attacks-2025/)).

GraphQL federation introduces supply chain risk when subgraphs are operated by different teams. **CVE-2026-32621** (Apollo Gateway, CVSS 9.9) enables prototype pollution from a malicious client or compromised subgraph through crafted field aliases and variable names, potentially altering gateway behavior across all clients ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2026-32621)). Leaked API keys remain an enormous problem: GitGuardian found **23.8 million secrets in public GitHub repositories in 2024** (25% year-over-year increase), Truffle Security found 543,699 secrets still authenticating across 224 million repositories, and **64% of secrets exposed in 2022 were still valid four years later** ([CyberNews](https://cybernews.com/security/github-exposed-credentials-contain-thousands-gemini-keys/)). Automated scanners now specifically target AI API keys -- Cyble reported over 5,000 GitHub repositories exposed hardcoded ChatGPT API keys ([Cyble](https://cyble.com/blog/when-ai-secrets-go-public-chatgpt/)).

## Webhook SSRF via DNS rebinding defeats URL validation patterns

Webhook security vulnerabilities cluster around SSRF via user-controlled URLs, replay attacks from flawed timestamp validation, and signature bypass through timing side-channels. The DNS rebinding variant is particularly dangerous because it defeats the most common defense: validate-then-request. MLflow's webhook URL validation (GitHub Issue #24179) discards the resolved IP on success and independently re-resolves the hostname for the actual request -- a DNS rebinding attacker with short TTL returns a public IP for validation, then flips to 169.254.169.254 before the real request ([MLflow](https://github.com/mlflow/mlflow/issues/24179)). **CVE-2025-64522** (Soft Serve) had no webhook URL validation at all, and HTTP responses stored in delivery logs provided the exfiltration path for internal service data ([GitLab Advisory](https://advisories.gitlab.com/golang/github.com/charmbracelet/soft-serve/CVE-2025-64522/)). **CVE-2026-12726** (AWX) exploited the unvalidated `statuses_url` field in GitHub webhook payloads to exfiltrate PAT credentials ([Stack.watch](https://stack.watch/vuln/CVE-2026-12726/)).

Replay attacks exploit canonicalization inconsistencies: **CVE-2026-41351** (OpenClaw/Telnyx) used Base64 vs. Base64URL encoding to produce different replay cache keys for the same signature, and **CVE-2026-41395** (OpenClaw/Plivo, CVSS 8.2) exploited query-parameter reordering between signature computation and replay detection ([Wiz](https://www.wiz.io/vulnerability-database/cve/cve-2026-41351); [Feedly](https://feedly.com/cve/CVE-2026-41395)). Timing attacks on signature verification affect production software -- **CVE-2022-24912** (Atlantis) and **CVE-2026-70437** (Jenkins) both used non-constant-time comparison that leaks timing information enabling secret recovery ([NVD](https://nvd.nist.gov/vuln/detail/cve-2022-24912); [SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-70437/)). Defense requires IP pinning at dial time (resolve once, connect to the resolved IP), constant-time signature comparison, timestamps with tight acceptance windows, delivery ID tracking for replay prevention, and allowlisting webhook destinations rather than blocklisting dangerous ranges.

## Mobile API attacks extract secrets through instrumentation and deep link exploitation

Certificate pinning bypass via Frida and Objection remains the standard first step in mobile API testing, with prebuilt SSL pinning disable commands bypassing pinning in **19 of 28 apps tested** in one vendor's assessment ([SecureWare](https://www.secureware.co.uk/blog/certificate-pinning-bypass-2025)). HTTP Toolkit's `frida-interception-and-unpinning` repository maintains patches for many known pinning libraries plus a fallback for obfuscated Android apps ([GitHub](https://github.com/httptoolkit/frida-interception-and-unpinning)). Native-code pinning (.so files) requires finding the correct function offset through static analysis with Ghidra, and Swift URLSession delegates with LLVM-obfuscated binaries require decompilation before a bypass script can be written. API keys embedded in mobile apps are recoverable through decompilation (JADX, APKTool) or runtime hooking (Frida intercepting SharedPreferences access or network requests). The `AndroidManifest.xml`, `res/values/strings.xml`, `assets/`, and `.so` native libraries are standard locations for embedded secrets ([HackerNoon](https://www.hackernoon.com/hack-your-app-before-hackers-do-2025s-mobile-pentesting-playbook)). No client-side secret storage is sufficient against a determined attacker -- backend proxy patterns where the mobile app authenticates to a backend that holds API keys are the only reliable mitigation ([Approov](https://approov.io/blog/how-to-extract-an-api-key-from-a-mobile-app-with-static-binary-analysis)).

Deep link vulnerabilities remain an underexplored attack surface. A February 2025 pentest discovered a deep link parsing flaw combined with path traversal and open redirect on the API domain, resulting in leaked access tokens and full account takeover ([DeepStrike](https://deepstrike.io/blog/full-account-takeover-through-deeplink-vulnerability)). Custom URI schemes are open by default and exploitable via intent hijacking -- a malicious app registering the same scheme intercepts links intended for the legitimate app. Client-side authentication bypass (biometric bypass via Frida hooking the authentication callback to always return success, response modification in proxy to change `"isPremium": false` to `true`) exploits the fundamental weakness that any security decision made client-side is a suggestion, not a control ([HackerNoon](https://www.hackernoon.com/hack-your-app-before-hackers-do-2025s-mobile-pentesting-playbook)).

## Business logic race conditions and price manipulation evade all automated scanners

Business logic attacks constituted **27% of API attacks in 2023, up from 17% the year before** ([APISec.ai](https://www.apisec.ai/blog/race-condition-vulnerabilities-in-apis)). The HTTP/2 single-packet attack technique (James Kettle, 2023) reduced race-condition exploit time from over two hours to approximately **30 seconds** by queuing requests behind a gate and releasing them in a single TCP packet -- for HTTP/1.1, last-byte synchronization achieves similar timing. Common targets include balance transfers (double-spend), coupon redemption (multiple uses of single-use codes), limited stock (over-purchase), and rate-limit bypass. A bug bounty write-up describes an insurance platform where parallel GraphQL "create profile" requests resulted in duplicate profile creation ([Medium](https://medium.com/@info.adityabhatt3010/bug-bounty-race-exploiting-race-conditions-for-infinite-discounts-a2cb2f233804)).

Multi-step workflow manipulation exploits client-supplied values for server-authoritative data. Sending `"total": 0.01` in a checkout completion request where the original total was $499.99 succeeds when the endpoint accepts client-supplied prices instead of recalculating from the catalog ([Intigriti](https://www.intigriti.com/blog/news/top-6-price-manipulation-vulnerabilities-ecommerce)). Negative quantity attacks (`"quantity": -1`) cause the server to subtract item prices from the cart total when the spec never required positive values ([DEV Community](https://dev.to/roxdavirox/business-logic-in-e-commerce-apis-price-manipulation-negative-quantity-and-coupon-abuse-19pi)). Currency rounding attacks remain viable -- Check Point reported a **$128M exploit** against Balancer V2 pools exploiting integer division truncation ([Check Point](https://research.checkpoint.com/2025/how-an-attacker-drained-128m-from-balancer-through-rounding-error-exploitation/)). Idempotency keys become attack vectors when not bound to the request body hash and authenticated user, enabling cross-operation key reuse. A 2026 arXiv paper formalizes reward engines as state machines with two integrity invariants (rewards only for qualifying transactions, refund consistency) and documents the "Double Dip" attack where refunds are processed but rewards retained ([arXiv](https://arxiv.org/pdf/2604.16427)).

## Advanced CORS exploitation chains subdomain takeover with origin validation regex flaws

The `null` Origin attack exploits the fact that browsers send `Origin: null` from sandboxed iframes, `file://` pages, and cross-origin redirects. If a server whitelists the literal string `null` with `Access-Control-Allow-Credentials: true`, any site can steal authenticated data through `<iframe sandbox="allow-scripts" srcdoc="...">` that sends credentialed fetch requests with the null origin ([Hackviser](https://hackviser.com/tactics/pentesting/web/cors-misconfiguration)). Subdomain takeover chains with CORS when a wildcard policy (`*.example.com`) trusts all subdomains and an unused subdomain's CNAME points to an unclaimed cloud resource -- the attacker claims it and serves JavaScript making credentialed requests trusted by the main API ([PayloadPlayground](https://payloadplayground.com/blog/cors-misconfiguration-exploitation-guide)). Regex-based origin validation produces systematic bypasses: **CVE-2026-25478** (Litestar, CVSS 7.4) matched `goodXexample` due to unescaped dots, **CVE-2026-40110** (Jupyter Server) matched `trusted.example.com.evil.com` because Python's `re.match()` only anchors at the start, and **CVE-2026-37737** (sanic-cors) had the identical `re.match` flaw ([Corgea](https://corgea.com/advisories/vulnerabilities/CVE-2026-25478); [Lutra Security](https://fieldguide.lutrasecurity.com/CVE-2026-40110/)). The Vary header introduces cache-layer CORS issues: **CVE-2026-59903** (Netty CorsHandler) overwrote a backend's `Vary: Authorization` header with `Vary: origin`, allowing caches to serve one user's sensitive response to another ([Netty Advisory GHSA-8c42-7qj2-3j46](https://github.com/netty/netty/security/advisories/GHSA-8c42-7qj2-3j46)).

## SSTI, deserialization, file upload, DNS rebinding, and Kubernetes API attacks round out the threat landscape

**Server-side template injection via API parameters** occurs when JSON body fields flow to template engines unsanitized. Most API scanners miss this because they probe XSS payloads, not template syntax like `{{7*7}}` or `${7*7}`. Detection injects arithmetic expressions: `{{7*'7'}}` returns `7777777` in Jinja2 and `49` in Twig. Impact reaches RCE because engines like Jinja2, FreeMarker, and EJS have full runtime access ([HackTricks](https://hacktricks.wiki/en/pentesting-web/ssti-server-side-template-injection/index.html); [PayloadsAllTheThings](https://github.com/swisskyrepo/PayloadsAllTheThings/blob/master/Server%20Side%20Template%20Injection/README.md)).

**Insecure deserialization** in API backends remains critical: Jackson's JSON type hints (`@class`, `@type`) turn endpoints into arbitrary class instantiation vectors with blocklists repeatedly bypassed, Newtonsoft.Json is dangerous when `TypeNameHandling` is not `None`, and **CVE-2025-32444** (vLLM, CVSS 10.0) shows pickle-based deserialization in AI inference frameworks ([chs.us](https://chs.us/guides/deserialization/)). The "Sleeping Giants" research (April 2025) demonstrates that supply chain attacks can introduce partial gadget chain components into libraries through seemingly benign contributions ([arXiv](https://arxiv.org/pdf/2504.20485)).

**File upload polyglot attacks** create files valid in multiple formats (JPEG header + PHP code) that bypass magic-byte validation. **CVE-2025-55298** (ImageMagick format string bug) enables RCE when processing attacker-supplied images ([GitHub Advisory GHSA-9ccg-6pjw-x645](https://github.com/advisories/GHSA-9ccg-6pjw-x645)). Path traversal via multipart `filename` fields (e.g., `../../../etc/passwd`) writes files to arbitrary locations. SVG uploads containing embedded JavaScript execute in the viewer's browser context when served as `image/svg+xml`.

**DNS rebinding against internal APIs** exploits the TOCTOU gap between hostname validation and the actual request. **GHSA-6653-vcx4-69mc** (Paperless-ngx) and **CVE-2025-69660** (simstudioai/sim) confirm active exploitation. The MCP TypeScript SDK prior to version 1.24.0 lacked DNS rebinding protection by default, making local MCP servers accessible to attacker-controlled web pages ([Varonis](https://www.varonis.com/blog/model-context-protocol-dns-rebind-attack)). NCC Group's Singularity tool documents bypass techniques: using `0.0.0.0` to reach localhost (bypassing `127.0.0.1` blocks), CNAME records pointing to internal IPs, and IPv6 `::1` ([Singularity](https://github.com/nccgroup/singularity/wiki/Protection-Bypasses)). Defense requires DNS pinning: resolve once, validate the IP, and connect to the resolved IP using a custom dialer.

**Kubernetes API attacks** primarily stem from misconfiguration rather than novel exploits. One campaign reportedly compromised **60+ clusters** through API servers with anonymous authentication enabled ([AlertLogic](https://support.alertlogic.com/hc/en-us/articles/360003799632-Kubernetes-Unauthenticated-API-Access)). Direct etcd access gives cluster-admin rights because etcd stores all secrets in plaintext by default. The kubelet API accepts anonymous requests and is not subject to admission control or audit logging ([Aqua Security](https://www.aquasec.com/blog/kubernetes-exposed-exploiting-the-kubelet-api/)). **CVE-2025-1974** (ingress-nginx, CVSS 9.8) allowed unauthenticated code execution in the controller with cluster-wide secret access ([NCSC Ireland](https://ncsc.gov.ie/pdfs/2503250145_Vulns_Kubernetes_Ingress-NGINX.pdf)). Shadow and zombie APIs compound these risks: Salt Security's 2024 report named zombie APIs as organizations' top API security concern, and attackers discover them through JavaScript analysis (LinkFinder), wordlist fuzzing (ffuf), traffic analysis, and Wayback Machine archives ([Salt Security](https://salt.security/blog/are-your-apis-plotting-against-you); [YesWeHack](https://www.yeswehack.com/learn-bug-bounty/discover-map-hidden-endpoints-parameters)).

## Conclusion

The API threat landscape in 2025-2026 has shifted decisively from application-layer vulnerabilities toward protocol, infrastructure, and trust-boundary exploitation. The most dangerous attacks -- HTTP/2 desync, gRPC schema poisoning, MCP tool poisoning, service mesh sidecar injection, and AI gateway supply chain compromise -- operate at layers that conventional API security testing does not reach. Three architectural patterns account for the majority of these vulnerabilities: parsing differentials between components (gateway vs. backend path normalization, WAF vs. application JSON parsing, CDN vs. origin URL interpretation), implicit trust across service boundaries (microservice-to-microservice token reuse, GraphQL federation subgraph trust, webhook URL validation), and client-side security enforcement (mobile authentication bypass, business logic validation, CORS origin checks). Organizations that rely solely on OWASP API Top 10 coverage and traditional DAST scanning miss the attack categories documented here -- which collectively represent the techniques that produce the highest-value bug bounties, the most critical CVEs, and the most impactful real-world breaches. Closing these gaps requires protocol-aware testing tools (HTTP/2 smuggling detection, gRPC reflection probing, WebSocket hijacking checks), infrastructure-layer security assessment (service mesh configuration audit, Kubernetes API exposure review, serverless event source validation), and business-logic testing that cannot be automated (state machine bypass, race condition exploitation, reward system integrity verification).
