# Breaking hardened CodeIgniter through layer confusion and OTP flaws

When standard vulnerability classes test clean across 200+ responses, the attack surface shifts from the application's inputs to the seams between its layers. Against a hardened CodeIgniter + Apache stack with OTP-based admin authentication, the most productive path forward is exploiting **parser differentials between Apache and CodeIgniter's router**, **framework-level CVEs disclosed in 2024-2026** (three critical CVEs fixed in CI4 v4.7.4 alone), **race conditions and parameter tampering in OTP validation**, and **business logic gaps that survive input hardening**. The discovery of a legacy captcha-less OTP endpoint via `/admin/.` dot-segment normalization already proves that Apache and CodeIgniter disagree on path resolution -- a class of confusion that Orange Tsai's 2024 research formalized into nine CVEs and that produced fresh Apache vulnerabilities as recently as October 2026. The target's non-rotating CSRF tokens, previously reported document IDOR, and captcha-less legacy endpoint are individually low-severity findings that chain into medium-to-critical attack paths when combined with the techniques documented here. This report synthesizes the research into actionable test cases organized by the layer each technique targets.

## Apache and CodeIgniter path confusion unlocks bypasses beyond 72 traversal variants

The 72 path traversal variants that tested clean targeted a single vulnerability class. The productive attack surface lies instead in **semantic ambiguity** between how Apache resolves a URL and how CodeIgniter's router interprets the result -- what Orange Tsai formalized as "Confusion Attacks" at Black Hat USA 2024, yielding **nine CVEs across three attack classes**: Filename Confusion, DocumentRoot Confusion, and Handler Confusion ([Orange Tsai Blog](https://blog.orange.tw/posts/2024-08-confusion-attacks-en/)).

The most exploitable primitive is **`%3F` truncation in mod_rewrite backreferences** (CVE-2024-38474/38475). When a RewriteRule maps `/(.*) -> /app/$1`, requesting `/%3Fname=value` causes mod_rewrite to treat the decoded `?` as a query-string delimiter, truncating the filesystem path and potentially serving an unintended file. Apache versions **2.4.0 through 2.4.59** are affected; the fix landed in 2.4.60 ([Oracle Linux CVE Record](https://linux.oracle.com/cve/CVE-2024-38475.html)). A second critical primitive is **double URL-decoding via internal redirect**: any RewriteRule in per-directory context (including `.htaccess`) triggers an internal redirect that decodes the URL twice, so `%252e%252e` decodes to `%2e%2e` on the first pass and `..` on the second, bypassing single-decode traversal filters ([Orange Tsai Blog](https://blog.orange.tw/posts/2024-08-confusion-attacks-en/)).

The target's existing `/admin/.` finding directly implicates this class. **CVE-2026-79768**, disclosed October 1, 2026, confirms that `/./` in mod_userdir with an absolute UserDir creates path-equivalence flaws in Apache **2.4.0 through 2.4.68**, fixed in 2.4.69 ([Wiz Vulnerability Database](https://www.wiz.io/vulnerability-database/cve/cve-2026-79768)). A separate 2025 finding demonstrated that **Nginx and Apache disagree on the same path** in PAN-OS (CVE-2025-0108), where authentication set at the Nginx layer was bypassed because Apache handled the path differently ([Assetnote Research](https://www.assetnote.io/resources/research/nginx-apache-path-confusion-to-auth-bypass-in-pan-os)). Even systems patched for the 2024 CVEs face **CVE-2026-42356**, a handler confusion after internal redirects affecting Apache 2.4.60-2.4.68, fixed in 2.4.69 ([Apache Security Advisories](https://httpd.apache.org/security/vulnerabilities_24.html)).

Beyond path confusion, **HTTP verb tampering** bypasses `.htaccess` rules that use `<Limit GET POST>` instead of `<LimitExcept>`. Any method not listed -- HEAD, OPTIONS, PATCH, or an invented verb like `FOOBAR` -- bypasses the access restriction entirely while CodeIgniter still routes the request to the controller ([Acunetix](https://acunetix.com/vulnerabilities/web/http-verb-tampering)). Additionally, Apache and PHP-FPM can disagree on `SCRIPT_NAME`, `PATH_INFO`, and `PHP_SELF` when `ProxyPass` or `mod_rewrite` is used instead of `SetHandler`, creating a gap where the CI router sees different path segments than Apache's access controls evaluated ([PHP Bug #65641](https://bugs.php.net/65641)). The `AllowEncodedSlashes NoDecode` directive compounds this: Apache's `<Location>` ACLs match against the decoded path while the PHP framework routes on the raw URI, so a `%2F` in the right position bypasses Apache-level access control while still reaching the intended CI controller ([Red Hat RFE](https://access.redhat.com/node/465853)).

The following test patterns extend beyond the 72 standard variants and target these specific parser differentials. All require `curl --path-as-is` to prevent client-side normalization:

| Technique | Example Path | CVE / Basis |
|---|---|---|
| %3F truncation | `/admin%3F.php`, `/admin%3Fname=value` | CVE-2024-38474 |
| Double decode | `/%252e%252e/admin`, `/public/%252e%252e/admin/index.php` | Orange Tsai internal redirect |
| Dot-segment variants | `/admin/.`, `/admin/./`, `/admin/%2e`, `/admin/foo/../` | CVE-2026-79768 |
| Encoded slash | `/admin%2Fhidden`, `/index.php%2Fadmin%2Fdashboard` | AllowEncodedSlashes |
| PATH_INFO injection | `/index.php/admin/dashboard`, `/known-public.php/admin/secret` | PHP Bug #65641 |
| Verb tampering | `OPTIONS /admin/`, `PATCH /admin/`, `FOOBAR /admin/` | Apache `<Limit>` misconfiguration |
| Host header | `Host: localhost`, `Host: 127.0.0.1`, duplicate Host headers | OWASP host header injection |
| Trailing characters | `/admin%20/`, `/admin%09/`, `/admin;/`, `/ADMIN/` | Parser differential |

## CodeIgniter framework CVEs from 2024-2026 expose upload, query, and validation surfaces

CodeIgniter 4 accumulated a cluster of **critical CVEs in 2026** that any target running below version 4.7.4 should be tested against. The most severe is **CVE-2026-63221** (CVSS 9.4): the Query Builder's `deleteBatch()` method substitutes bound values from `where()` conditions into generated SQL while ignoring their escape flags, enabling SQL injection. Regular `delete()` is unaffected; only `deleteBatch()` with `where()` conditions triggers the flaw. Versions **4.3.0 through 4.7.3** are affected ([Averlon Research](https://research.averlon.ai/vulnerability-intelligence/cve/CVE-2026-63221)).

File upload validation received two critical bypasses in the same release cycle. **CVE-2026-48062** (CVSS 9.8) revealed that the `ext_in` validation rule used `$file->guessExtension()` (MIME-based) rather than `$file->getClientExtension()` (filename-based), so an attacker could upload `shell.php` containing GIF magic bytes and pass `ext_in[avatar,gif]` validation ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-48062/)). **CVE-2026-63223** (CVSS 9.8) showed that `is_image` and `mime_in` rules do not independently enforce safe client filename extensions, allowing executable content upload when the application preserves client filenames in web-accessible directories ([Averlon Research](https://research.averlon.ai/vulnerability-intelligence/cve/CVE-2026-63223)). A companion path traversal, **CVE-2026-63222** (CVSS 7.5), showed that `UploadedFile::move()` without a second argument uses the unsanitized client filename ([Rapid7](https://www.rapid7.com/db/vulnerabilities/cve-2026-63222/)). These three chain into a single RCE path: MIME bypass plus path traversal equals web shell.

An older but still relevant finding is **CVE-2023-32692** (CVSS 9.8): Remote Code Execution via Validation Placeholders in CI4 versions below 4.3.5, with a public proof of concept available. This bypasses all application-level security measures through the Validation library ([Averlon Research](https://research.averlon.ai/vulnerability-intelligence/cve/CVE-2023-32692)). In 2025, **CVE-2025-54418** disclosed ImageMagick command injection in CI4 below 4.6.2 ([Packagist Advisories](https://packagist.org/packages/codeigniter4/framework/advisories)), and **CVE-2026-63220** showed that `IncomingRequest::isSecure()` trusted `X-Forwarded-Proto` and `Front-End-Https` headers from any request, allowing HTTPS spoofing -- exploitable when the backend is directly reachable over HTTP or when access control decisions depend on `isSecure()` ([ReleaseAlert](https://releasealert.dev/cve/CVE-2026-63220)).

On the routing side, CodeIgniter 4's **Auto Routing (Legacy)** is the single largest source of routing-related security issues. The official documentation warns that it "sends a request using any HTTP method to a controller method" and is "easy to create vulnerable apps where controller filters or CSRF protection are bypassed" ([CI4 Security Docs](https://codeigniter4.github.io/userguide/concepts/security.html)). CVE-2022-24712 demonstrated this concretely: with auto-routing enabled, controllers that did not explicitly check the request method were exploitable for CSRF bypass ([GitHub Advisory GHSA-4v37-24gm-h554](https://github.com/codeigniter4/CodeIgniter4/security/advisories/GHSA-4v37-24gm-h554)). For CI3 targets specifically, no CVEs appeared in 2024-2026, but CI3 reached end of life, and its cookie-based sessions, `xss_clean()` blacklist filter (bypassed repeatedly via CVE-2012-1915, CVE-2013-4891, and multiple GitHub issues), and session fixation flaw (CVE-2018-12071, pre-3.1.9) remain relevant attack surface ([Neal Poole Blog](https://nealpoole.com/blog/2013/07/codeigniter-21-xss-clean-filter-bypass/); [Vulert](https://vulert.com/vuln-db/CVE-2018-12071)).

The first testing priority is version fingerprinting: check `Server` response headers, error page styling differences between CI3 and CI4, exposed `composer.json` or `composer.lock` files, and the default CI error page that reveals the version. Every CI4 target below 4.7.4 should be tested for the three 2026 upload/query CVEs, and every CI4 target below 4.3.5 should be tested for the validation placeholder RCE.

## OTP authentication yields to race conditions, parameter tricks, and response manipulation

The target's OTP-based admin login presents attack surface across four distinct technique classes, each validated by **multiple CVEs disclosed in 2025-2026**. The most technically sophisticated is the **race condition in OTP consumption**. CVE-2026-85237 (MISP, CVSS 8.6) demonstrated that when the OTP is read from the store, validated, and then deleted in separate non-atomic steps, parallel requests slip through -- one code produced two valid sessions ([OpenCVE](https://app.opencve.io/cve/CVE-2026-85237)). CVE-2026-72584 (fastschema, CVSS 7.4) showed the same pattern in attempt-limit bypasses: the system reads the counter, then updates it in a separate step, and concurrent requests exceed the limit before the update lands ([OpenCVE](https://app.opencve.io/cve/CVE-2026-72584)). Parse Server's MFA recovery codes (CVE-2026-107276) confirmed that a single recovery code could be reused through concurrent login requests ([OpenCVE](https://app.opencve.io/cve/CVE-2026-107276)). Testing requires **HTTP/2 single-packet attacks** via Burp Suite's Turbo Intruder: send 20-50 identical OTP verification requests simultaneously within a single TCP packet, ensuring sub-millisecond arrival synchronization. A 2025 academic paper introduces **QUICker**, the first HTTP/3 race condition tool, enabling exploitation of race windows previously too narrow to target ([ScienceDirect](https://www.sciencedirect.com/science/article/pii/S0167404825004298)).

**Brute-force with rate limit bypass** remains viable. CVE-2026-8760 (WordPress "Login with OTP" plugin, CVSS 9.8) showed a misplaced rate limit on the validation endpoint that left 6-digit OTPs guessable ([ZeroPath Blog](https://researcher.branch.zeropath.com/blog/cve-2026-8760-wordpress-login-otp-authentication-bypass)). CVE-2026-33640 (Outline, CVSS 9.1) showed codes not invalidated after repeated bad submissions, depending entirely on a bypassable rate limiter ([GCVE](https://db.gcve.eu/vuln/CVE-2026-33640)). Rate limits keyed on IP can be bypassed via `X-Forwarded-For` header rotation ([System Weakness](https://systemweakness.com/brute-forcing-otp-via-bypassing-rate-limit-c5ee6b25c2a8)). Per-session rate limits are weaker than per-account limits because opening multiple sessions resets the counter.

**Response manipulation** exploits the gap between server-side validation and client-side flow control. A documented bypass changed a 500 error to 200 OK in Burp Suite's response interception, and the application proceeded to the authenticated state ([Noor Homaid Medium](https://noorhomaid.medium.com/bug-bounty-writeup-2f-otp-bypass-on-registeration-via-response-manipulation-2e53573ffa4c)). JSON body tampering -- changing `"verified": false` to `"verified": true` or `"status": "failed"` to `"status": "ok"` -- works when the server does not maintain server-side session state tracking actual OTP validation ([DEV Community](https://dev.to/blue_byte/2fa-bypass-via-response-manipulation-4062)). CVE-2026-56073 (Cap-go) formalized this as CWE-345: Insufficient Verification of Data Authenticity ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2026-56073/)).

**Parameter tampering** targets the OTP field itself. Systematic tests include: removing the OTP parameter entirely, sending empty strings, null values, boolean `true`, all-zeros (`000000`), arrays (`otp[]=1234&otp[]=5678`), an array of all possible values in a single request, and SQL/NoSQL injection payloads (`' OR '1'='1`, `{"$gt": ""}`) ([OWASP WSTG-ATHN-11](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/04-Authentication_Testing/11-Testing_Multi-Factor_Authentication); [GitHub Bug-Bounty-Methodology](https://github.com/tuhin1729/Bug-Bounty-Methodology/blob/main/2FA.md)). PHP's type juggling is particularly dangerous here: `"0" == false` and `null == false` comparisons can cause bypass when the server uses loose comparison. **Phone number format manipulation** -- appending whitespace, toggling country codes, using URL encoding -- resets rate limits by causing the server to treat modified strings as new requests. A BookMyShow bug bounty paid **1000 INR** for exactly this: appending a space to the phone number bypassed the rate limit ([InfoSec Write-ups](https://infosecwriteups.com/how-i-bypassed-bookmyshows-otp-limit-with-just-a-space-got-1000-for-it-70eab29fb6aa)).

The legacy captcha-less OTP endpoint discovered via `/admin/.` amplifies every technique above. Without captcha, automated brute-force, race condition exploitation, and SMS bombing all proceed without the bot-detection barrier that protects the main login. This endpoint should also be tested for whether it accepts OTP verification requests, not just OTP sending requests.

## Session puzzling, stale tokens, and legacy endpoints erode hardened defenses

**Session puzzling** (session variable overloading) bypasses authentication by populating session state through an unprotected flow and then accessing a protected one. OWASP documents this as WSTG-SESS-08: the same session variable serves multiple purposes across different application flows, enabling authentication bypass, impersonation, and privilege escalation ([OWASP WSTG v4.1](https://owasp.org/www-project-web-security-testing-guide/v41/4-Web_Application_Security_Testing/06-Session_Management_Testing/08-Testing_for_Session_Puzzling.html)). PHP's `$_SESSION` superglobal stores all session data in a single associative array, making variable overloading likely when developers use generic key names like `verified`, `authenticated`, or `user_role` ([Invicti](https://www.invicti.com/blog/web-security/two-interesting-session-related-vulnerabilities)). The test procedure is: map all flows that set session variables (login, password reset, registration, profile update, OTP verification), then attempt to reach the post-OTP-verified state by completing a different flow first -- for instance, complete a password reset flow, then navigate to the admin dashboard without completing OTP. A parallel session attack tests whether OTP verification is session-specific or account-wide: complete OTP in one browser session, then check if another concurrent session also gains access.

CodeIgniter's cross-cookie session access vulnerability (CVE-2022-46170) demonstrated a related flaw in CI4: when an application uses multiple session cookies with database/Memcached/Redis handlers, possession of one cookie grants access to pages requiring the other, fixed in 4.2.11 ([OSV](https://osv.dev/vulnerability/CVE-2022-46170)). CI3's session fixation vulnerability (CVE-2018-12071, pre-3.1.9) compounds this: if session IDs can be fixed, the attacker controls the session state into which puzzling payloads are injected ([Vulert](https://vulert.com/vuln-db/CVE-2018-12071)).

The target's **non-rotating CSRF tokens** (valid for the entire session) create additional attack surface. CodeIgniter 3 uses per-session tokens by default (`$config['csrf_regenerate']` is `FALSE`), and CI4 offers per-request regeneration only when `$csrfRegenerate` is explicitly set to `TRUE` ([PentesterLab](https://pentesterlab.com/glossary/csrf-token)). A leaked non-rotating token remains valid for the session duration. Testing should include: reusing a captured token after logout and re-login; testing cross-user token acceptance (does user A's token work for user B's session); checking whether the token is derived from the session ID (making it predictable if the session ID is known); and testing **login CSRF + token fixation**: force the victim to log into the attacker's account, the application sets the attacker's CSRF token in the victim's browser, then the attacker can craft CSRF attacks using their known token ([Ruby on Rails Security Discussion](https://discuss.rubyonrails.org/t/security-says-csrf-token-should-be-a-nonce/89189)). CVE-2022-35943 showed that SameSite attackers controlling a subdomain can bypass CodeIgniter's CSRF protection in both cookie and session modes ([GitHub Advisory GHSA-5hm8-vh6r-2cjq](https://github.com/codeigniter4/shield/security/advisories/GHSA-5hm8-vh6r-2cjq)).

The **legacy captcha-less OTP endpoint** exemplifies stale endpoint exploitation. A semicolon appended to an endpoint path bypassed an edge proxy's block while the backend accepted the variant, earning a **$175 Bugcrowd bounty** ([Exploit-DB Paper 48084](https://www.exploit-db.com/docs/48084)). CVE-2025-42601 demonstrated captcha bypass in Meon KYC: a remote attacker intercepted a request, stripped the captcha parameter, and submitted without solving it ([SentinelOne](https://www.sentinelone.com/vulnerability-database/cve-2025-42601/)). For the target, the legacy endpoint that lacks captcha but still sends OTPs is a **reportable SMS bombing vector**. CloudSEK identified approximately **843 vulnerable API endpoints** lacking rate limiting or captcha on OTP endpoints across e-commerce, financial, government, and telecom organizations ([The Cyber Express](https://thecyberexpress.com/tag/captcha/amp/)). The financial impact is concrete: at $0.01-0.05 per SMS, 10,000 automated requests cost the target $100-500. Combined with MFA fatigue -- flooding the admin with OTPs until they approve one reflexively -- this escalates from nuisance to account compromise ([Authgear](https://www.authgear.com/post/otp-bots-bypass-sms-2fa/)).

## Novel techniques, IDOR depth, and unconventional vectors complete the attack map

**Second-order injection** targets the gap between safe storage and unsafe consumption. CodeIgniter's Query Builder parameterizes queries at insertion, but if stored values are later used in raw `$this->db->query()` calls, second-order SQL injection emerges. Registration fields like username or display name, stored safely and later used in admin dashboard queries, PDF generation, or log review queries, are prime candidates ([PortSwigger KB](https://portswigger.net/kb/issues/00100210_sql-injection-second-order)). The out-of-band variant uses DNS-based exfiltration through stored procedures ([NetSPI](https://www.netspi.com/blog/technical-blog/web-application-pentesting/second-order-sql-injection-with-stored-procedures-dns-based-egress/)). Second-order SSRF applies when stored URLs (webhook destinations, avatar URLs, document import URLs) are fetched later in background jobs.

**HTTP request smuggling** gained renewed relevance through James Kettle's **HTTP Terminator** (Black Hat USA 2026), an AI system that generated novel smuggling techniques and found **200-700 vulnerable targets** across 30,000 authorized sites ([CISO Platform](https://www.cisoplatform.com/profiles/blogs/session-highlights-field-notes-from-black-hat-def-con-2026-what-c)). Apache httpd has CVE-2023-25690 (mod_proxy smuggling, 2.4.0-2.4.55) and CVE-2026-63718 (mod_proxy_uwsgi response smuggling, 2.4.30-2.4.68) ([Apache Security Advisories](https://httpd.apache.org/security/vulnerabilities_24.html)). Testing uses CL-TE and TE-CL probe requests, chunked encoding variations (`Transfer-Encoding: xchunked`, `Transfer-Encoding : chunked` with space), and Burp Suite's HTTP Request Smuggler extension.

**Web cache poisoning** exploits parser discrepancies between CDNs/caches and the origin. PortSwigger's "Gotta cache 'em all" research demonstrated that path normalization differences let attackers trick caches into storing dynamic responses as static assets ([PortSwigger Research](https://portswigger.net/research/gotta-cache-em-all)). A ChatGPT account takeover used wildcard web cache deception with path traversal confusion to cache auth tokens ([PortSwigger Nominations 2024](https://portswigger.net/research/top-10-web-hacking-techniques-of-2024-nominations-open)). Test by sending requests like `/account/settings/..%2fstatic/logo.png` and checking whether the dynamic response is cached, and by injecting unkeyed headers (`X-Forwarded-Host`, `X-Forwarded-Proto`) that influence the response but are excluded from the cache key.

**Timing side-channels** bypass identical error messages. Even when valid and invalid phone numbers produce the same text response, database lookups for existing users take measurably different times. Statistical analysis over many requests detects differences of a few milliseconds, enabling username enumeration that standard testing misses. **Error-based template injection** -- the #1 technique in PortSwigger's Top 10 Web Hacking Techniques of 2025 -- adds two exploitation modes borrowed from SQL injection's playbook ([PortSwigger](https://portswigger.net/research/top-10-web-hacking-techniques-of-2025)). Test with template syntax in all input fields: `{{7*7}}` (Twig), `{php}echo 7*7;{/php}` (Smarty), and `<?= 7*7 ?>` (raw PHP), focusing on error pages, email templates, and PDF generation.

For the **/document endpoint** (previously reported IDOR), the testing must go deeper. IDORs remain prevalent because they require manual, creative testing that automated scanners cannot perform ([Instatunnel Substack](https://instatunnel.substack.com/p/insecure-direct-object-references)). The Burp Suite extension **Autorize** automates authorization checks by replaying every request with a low-privileged session while browsing as a high-privileged user ([Instatunnel Substack](https://instatunnel.substack.com/p/insecure-direct-object-references)). Test whether the previous IDOR fix checks that the user *owns* the document versus merely being *authenticated*. Test different HTTP methods (GET vs POST vs PUT) on the same endpoint. Check for authorization gaps between viewing/previewing and raw downloading/exporting. Check metadata endpoints for leaks even when document content is protected. **Mass assignment** testing adds `role=admin`, `is_admin=1`, `user_type=administrator`, or `group_id=1` to every POST/PUT endpoint in the admin panel, targeting profile updates, user creation, and settings changes ([OWASP WSTG](https://owasp.org/www-project-web-security-testing-guide/latest/4-Web_Application_Security_Testing/07-Input_Validation_Testing/20-Testing_for_Mass_Assignment)). In CI3's older Active Record pattern, mass assignment is less framework-managed and more ad-hoc, increasing the risk. **Unconventional input vectors** -- User-Agent, Referer, X-Forwarded-For, Accept-Language headers, and cookie values -- are frequently stored in databases or logs without sanitization, creating stored injection when viewed in admin log panels ([Akto Academy](https://akto.io/academy/http-header-injection)).

## Vulnerability chains and prioritized next-phase test cases

Chaining individually low-severity findings into demonstrated attack paths consistently increases bounty payouts -- documented examples show a jump from **$500 to $5,000** when an IDOR-plus-XSS chain was demonstrated ([InfoSec Writeups](https://infosecwriteups.com/from-500-to-5-000-how-chaining-idor-and-xss-led-to-mass-account-takeovers-ethical-hacking-a55de6e59a71)). At Black Hat USA 2026, three low-rated Microsoft flaws chained into full mailbox, calendar, SharePoint, and OneDrive exfiltration from one click on a microsoft.com link ([CISO Platform](https://www.cisoplatform.com/profiles/blogs/session-highlights-field-notes-from-black-hat-def-con-2026-what-c)). A four-link pre-auth RCE chain in WordPress core was discovered using AI assistance for **$25 of compute in 10 hours** ([CISO Platform](https://www.cisoplatform.com/profiles/blogs/session-highlights-field-notes-from-black-hat-def-con-2026-what-c)).

Five specific chains apply to this target. **Chain 1** (Medium): Legacy endpoint (`/admin/.`) + missing captcha = SMS bombing. The financial impact ($100-500 per 10K requests) plus MFA fatigue attack potential elevates this from informational to medium severity. **Chain 2** (Critical): Document IDOR + session puzzling = account takeover. Access admin documents via IDOR, extract session tokens or admin identifiers, then use session variable overloading to assume admin identity. **Chain 3** (High): User enumeration via timing + rate limit bypass on OTP = targeted account compromise. Different response times for valid/invalid phone numbers identify admin accounts, then OTP brute-force via header rotation breaks in. **Chain 4** (Medium-High): Non-rotating CSRF + login CSRF = session fixation chain. Force victim to log into attacker's account, then use the known CSRF token for state-changing attacks. **Chain 5** (High-Critical): Hidden endpoint discovery via JavaScript analysis + missing authorization = privilege escalation. Extract admin-only AJAX endpoints from JavaScript files, find they lack per-request authorization checks.

The following test cases should be executed next, ordered by expected impact-to-effort ratio. **Priority 1 -- Path confusion** (high impact, moderate effort): Run the full `%3F` truncation, double-decode, and dot-segment variant table against all admin paths; test HTTP verb tampering (`OPTIONS`, `PATCH`, `HEAD`, `FOOBAR`) against `/admin/` and all discovered admin sub-paths; probe `AllowEncodedSlashes` with `%2F`-encoded paths. **Priority 2 -- OTP race conditions** (critical impact, moderate effort): Use Turbo Intruder single-packet attack with 50 simultaneous OTP verification requests using the same valid OTP; test whether new sessions reset the attempt counter; test phone number format variations to bypass rate limits. **Priority 3 -- Legacy endpoint depth** (high impact, low effort): On the captcha-less `/admin/.` endpoint, test OTP brute-force, response manipulation, parameter tampering (empty/null/array OTP values), and measure SMS bombing rate. **Priority 4 -- Session puzzling** (critical impact, high effort): Map all session-setting flows, identify shared session variable names, attempt cross-flow state exploitation (password reset flow satisfying OTP verification check). **Priority 5 -- Framework CVE checks** (critical impact, low effort): Fingerprint the CI version and test applicable CVEs -- upload validation bypass (CVE-2026-48062/63223), `deleteBatch()` SQLi (CVE-2026-63221), validation placeholder RCE (CVE-2023-32692). **Priority 6 -- IDOR and access control** (high impact, moderate effort): Run Autorize across all admin functionality, test mass assignment parameters on every state-changing endpoint, test document endpoint with different HTTP methods and authorization gap between view/download. **Priority 7 -- Reconnaissance** (force multiplier, low effort): Download and analyze all JavaScript files with LinkFinder for hidden endpoints; check `/server-status`, `/server-info`, `.env`, `composer.json`; probe backup file extensions (`.bak`, `.old`, `.swp`, `~`) on known paths; use Wayback Machine for historical endpoint discovery.

## Conclusion

The gap between "standard tests clean" and "no vulnerabilities exist" is largest at architectural seams -- the points where Apache's path resolution disagrees with CodeIgniter's router, where OTP validation's check-and-consume steps are non-atomic, and where legacy endpoints predate modern security controls. The 2024-2026 research cycle produced a concentrated cluster of Apache path confusion CVEs (from Orange Tsai's Confusion Attacks through CVE-2026-79768), CodeIgniter framework CVEs (three critical flaws fixed in a single 4.7.4 release), and OTP bypass CVEs (seven high-to-critical disclosures confirming race conditions and missing rate limits as the dominant patterns). The target's existing findings -- the `/admin/.` normalization gap, the previously reported document IDOR, and the non-rotating CSRF tokens -- are chain links rather than endpoints, and their value multiplies when connected through the techniques documented here. The most immediate opportunity is the intersection of the captcha-less legacy endpoint with OTP race condition testing, where a single successful exploitation yields authentication bypass against the admin panel.
